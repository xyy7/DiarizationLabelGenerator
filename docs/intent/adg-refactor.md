## 一、确认的意图

### 产出物

把 ADG 从「纯前端手工标注工具」改造成**客户端–服务端的纠错式标注系统**。
服务端跑 DiariZen 出预标注、并持有音频 / 标注 / 任务状态；浏览器只是视图。

### 使用者

标注者本人及团队成员。**内部生产工具，非对外产品。**

### 为什么是现在

需要评测**第三方** diarization 模型，但必须基于**自有场景**的 ground truth。
现有工具在三个方面撑不住：多文件、团队协作、预标注工作流。

### 成功的样子

- 稳定产出**标准 10 字段 RTTM**，可直接喂给 `md-eval.pl` / `dscore` 计算 DER 而不出错
- 标注员的主要动作是「**改**」而不是「**画**」

### 约束

| 约束 | 影响 |
|---|---|
| DiariZen CPU ≈ 1x 实时（实测 30s 音频耗时 31s） | 推理**必须异步**：提交 → job id → 轮询/回调 → 取结果。GPU 只加速，不改变这个结构 |
| 预训练权重 CC BY-NC 4.0 | 仅限研究与学术用途，**不可商用** |
| 字幕为第二阶段 | 本期**保留** `TrackItem.text` 字段不动，但不为字幕投入额外工作 |

### 明确不做

- `ADG/improvements.md` 中的绝大多数条目（深色模式、VTT、音频淡入淡出、虚拟滚动、字幕样式……）
  —— 它们服务的是另一个产品定位，**建议整份删除重写**
- 浏览器内推理
- GPU 部署（未来考虑，不影响当前架构）
- `TrackItem.source: 'auto' | 'human'` provenance 字段（决策见下）
- 商用授权

## 二、已确认的缺陷（改造的事实依据）

以下均由代码扫描确认，非推测。

### 阻断性：当前导出的 RTTM 无法用于 DER 计算

**`ADG/src/utils/label.ts:40`**

```ts
const line = `SPEAKER ${fileName} ${channelIndex + 1} ${startTime} ${duration} <NA> <NA> ${speakerName} <NA> <NA> ${item.text || '<NA>'}`;
```

两个独立错误：

1. **第 3 字段填错**。RTTM 第 3 字段是**音频通道号**（单声道恒为 `1`），此处填的是**说话人序号**。
   结果：参考标注里 spk1 在 `chnl=1`、spk2 在 `chnl=2`……而 DiariZen 的假设文件全在 `chnl=1`。
   `md-eval` 按 channel 配对打分，**除首个说话人外全部判为 miss**，DER 数值无意义。

2. **字段数超标**。标准 RTTM 为 10 字段：
   `Type / FileID / ChannelID / tbeg / tdur / ortho / stype / name / conf / slat`
   此处 text 被追加为**第 11 字段**；转写文本的规范位置是**第 6 字段 `ortho`**。
   且默认文本为 `新标签`，未编辑的片段会全部带上它；文本含空格时字段数继续增长。
   `dscore` 等严格解析器会报错。

### 结构性：标注不跟随音频文件

**`ADG/src/types/index.ts`** — `channels` 挂在 `Project` 上，与 `audioFiles` 平级
**`ADG/src/store/index.tsx:67-76`** — `SET_CURRENT_AUDIO` 仅修改 `currentAudioId`

切换音频时 `channels` 原封不动，A 文件的片段会带到 B 文件上。
测试集天然包含几十上百个文件，**该结构等于不支持多文件标注**。

### 功能性：导入静默丢数据

**`ADG/src/App.tsx:133-137`** — 导入标签时只 dispatch 了 `channelName`，`items` 全部被丢弃，只建出空通道。
（`utils/label.ts:21-29` 的 `importLabels` 本身是正确的，问题在调用处。）

### 逻辑性：不可达分支

**`ADG/src/Timeline/index.tsx:404-406`** — 缩放刻度 `zoom >= 8 → 0.1` 永远走不到，被前一个 `zoom >= 5 → 0.5` 抢先匹配。

### 其他既有事实

- **无 RTTM 导入**（仅有导出）—— DiariZen 的产物进不来
- **零测试**：无测试文件、无测试依赖、无 `test` 脚本；唯一验证手段是 `tsc`
- **持久化仅 localStorage**：音频的 blob URL 刷新即失效，代码中主动剥离 `url`/`file` 字段
- `ADG/ARCHITECTURE.md` 描述的是**已废弃的旧数据结构**（`Label`/`Subtitle` 分离），与代码不符；
  `store/index.tsx:184-199` 保留着迁移旧数据的代码及两处 `@ts-ignore`
- `onPlaySegment` 属性层层传递但**从未被传入**，是死代码

## 三、四类改进方向

### ① 修复正确性缺陷

即上节四项。**全部位于纯函数中** —— 这正是单元测试的覆盖范围。

### ② 新建服务端

```
音频上传归档
  → 提交 diarize 任务（异步）
  → RTTM 回写为标注
  → 标注员认领文件 / 修正 / 标记完成
  → 导出标准 RTTM
```

一次性解决三个已确认问题：channels 不跟随音频、localStorage 存不下音频、团队成员看不到彼此数据。

### ③ 前端从「画」转向「改」

工作流常态已确认为：**DiariZen 先跑，人工修正**。当前主交互（空轨道拖拽画新片段）服务的是例外情况。

纠错工作流所需操作与现状对照：

| 纠错动作 | 现状 |
|---|---|
| 导入 RTTM 建通道 | 不存在 |
| 逐片段跳转 + 自动试听（听→判→改→下一个） | `onPlaySegment` 为死代码 |
| 片段改判给另一说话人 | 只能「在 A 删除、在 B 重画」 |
| 拆分（DiariZen 过分割） | 无 |
| 合并相邻片段 | 无 |
| 边界吸附播放头 / 微调 ±10ms | 无，仅能鼠标拖拽 |
| 跨说话人对齐看重叠 | 各通道时间轴独立，无法对齐 |

配套改动：

- **所有说话人共用一条时间轴**，缩放 / 滚动联动
- **快捷键重排**：`1`–`4` 当前绑定播放倍速（服务于「听」），应让位给「改判给说话人 N」（服务于「改」）；倍速另择键位
- `Timeline/index.tsx` 747 行、约 20 个 state，必然拆分

### ④ 补测试

**只测值得测的**：RTTM 序列化 / 解析、时间换算、拆分 / 合并、边界钳制。
上节全部四个 bug 均落在此范围内 —— 补测试不是「补最佳实践」，是这批缺陷的直接对策。
**不做 UI 快照测试。**

## 四、访谈中被推翻或调整的判断

留档以免重复讨论。

| 初始判断 | 结论 |
|---|---|
| 字幕系统是冗余包袱，应删除 | **错**。代码中 `Label`/`Subtitle` 早已合并为 `TrackItem`，「说话人 + 文本」模型已存在。且字幕是明确的第二阶段需求，`text` 字段保留 |
| 应加 `source: 'auto'\|'human'` 记录预标注来源，防止 DER 偏低 | **降级为可选**。测试集用于评测**第三方**模型，DiariZen 仅为加速器，锚定偏差的担忧不成立。<br>唯一残留理由：该字段可度量 DiariZen 在自有场景下的编辑率——若其在本领域表现很差，预标注可能是负收益，而需要数据才能判断 |
| 后端可能只需做推理服务，ADG 保持纯前端 | **否**。已确认音频、标注、任务状态均归属服务端，浏览器仅为视图 |
